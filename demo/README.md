# Demo video

A 40-second sales video for the buyers of this service: business owners and office or operations staff who type receipts in by hand. It is rendered as code. Every frame is drawn with Pillow from the pipeline's own output, replayed from recorded answers. Rendering needs no API key and costs nothing, and the video cannot show a value the pipeline did not produce. The headline on each shot carries the message, so the video works with the sound off. An AI voice narrates it, and the closing frame says so.

| Shot | Seconds | On screen | Headline | Spoken |
| --- | --- | --- | --- | --- |
| 1 | 5 | The receipt already done: every field filled in | Still typing receipts by hand? There's a faster way. | Imagine never typing in another receipt. |
| 2 | 5 | A pile of fictional receipts | Every week, someone retypes all of these. | The same pile, every week. One typo away from a wrong total. |
| 3 | 10 | The fields fill in one by one; each value's words are highlighted on the receipt | Vendor, date, total: filled in, each with the words it came from. | Now every receipt is entered for you. And you can see exactly where each number came from. |
| 4 | 6 | Currency: "Not on the receipt", with the reason | Not on the receipt? Left empty, never guessed. | If it's not on the receipt, it stays blank. No guesses. Ever. |
| 5 | 8 | A second receipt with a faded total, flagged "A person checks" ([`receipt-review.png`](receipt-review.png)) | Too faint to be sure? Flagged for a person to check. | Too faint to trust? It's flagged, so a person double-checks it. |
| 6 | 6 | Both receipts, a "Send me a sample" button and "Voice-over generated by AI" | Your documents, your spreadsheet. Send me a sample. | Send a few of your own receipts, and see them done. |

[`storyboard.py`](storyboard.py) holds the shots, their headlines and their spoken lines. [`evidence.py`](evidence.py) gathers what they show. [`render.py`](render.py) turns them into the video.

## Render

You need Docker and the OCR model (`uv run poe fetch-tessdata`).

```sh
uv run poe demo
```

The command builds the image in [`Dockerfile`](Dockerfile), which holds this project's locked environment plus ffmpeg, and runs `render.py` in it:

1. It replays both receipts and finds each quote's words with OCR's own word boxes.
2. It draws every frame and saves the stills to `.cache/demo/frames`, so they can be checked by eye.
3. It streams the frames to ffmpeg, each held for its duration. Frames within a shot dissolve into each other. Between shots, the picture dips to the background, so two headlines never overlap.
4. It lays each shot's committed voice-over clip under the picture, 0.3 s into the shot, and brings the voice to one loudness in two passes of ffmpeg's `loudnorm`.
5. It writes `.cache/demo/doc-intake-demo.mp4`: H.264 video with AAC audio (48 kHz, mono).

The render prints each shot's length, and fails if the video runs over 60 s or 10 MB, or if a recording or a voice-over clip is missing. Check the stills and the video, not only the green render.

## What it replays

Both receipts are answered by Claude and the answers are recorded in [`recordings/`](recordings). They are public, because the receipts are ours. Every recording is keyed by the prompt, schema, OCR text, page image and model (`evals/recording.py`). A change to any of them leaves the demo with nothing to replay, and [`tests/test_demo.py`](../tests/test_demo.py) fails first.

To record again (paid, run on purpose), use the provider and model the render uses, so no `.env` or shell setting changes the keys:

```sh
export DOC_INTAKE_PROVIDER=claude DOC_INTAKE_CLAUDE_MODEL=claude-opus-5-5
uv run poe extract --record demo/recordings demo/receipt.png          # about US$ 0.02
uv run poe extract --record demo/recordings demo/receipt-review.png   # about US$ 0.02
```

Then commit `demo/recordings`.

To change a receipt, edit [`make_receipt.py`](make_receipt.py), run `uv run python -m demo.make_receipt`, and record its answer again. The PNGs are committed rather than regenerated, since another Pillow version could change a pixel, and with it the recording key. A test checks that the generator still draws them. The pile in shot 2 is drawn on the fly: the pipeline never reads it, so it has no recording.

## Voice-over

The render never generates speech: it reads one committed WAV per spoken line from [`voice-clips/`](voice-clips). A clip is named by a key over its words and every setting of the voice ([`narration.py`](narration.py)), so a changed line can never pick up an old clip, and [`tests/test_demo.py`](../tests/test_demo.py) fails first, naming the command. After changing a line:

```sh
uv run poe demo-voice
```

It generates the missing clips locally, free and on CPU, in about a second each, and lists the clips no line uses any more, for you to delete. The first run downloads the voice (about 350 MB, checked by SHA-256) into `.cache/voice`. Then commit `demo/voice-clips`.

[`voice.py`](voice.py) is the one script that speaks. It runs on its own Python 3.13 and lock ([`voice.py.lock`](voice.py.lock), PEP 723), because Kokoro's package does not install on this project's Python 3.14. To update its packages, edit the pins and the `exclude-newer` date in its header, run `uv lock --script demo/voice.py`, and generate every clip again (delete `demo/voice-clips/*.wav` first). The key covers the voice, not the package versions, so listen to the result.

## Decisions (#45)

**Written for the buyer, not for developers.** The #39 video was a terminal screencast, and a client could not follow it. A first redo still had a shot on the eval gate ("a change that makes answers worse is blocked"). The owner cut it: that sells engineering practice to programmers, not an outcome to a client. The video now shows what the buyer gets, and nothing about how it is built. Testing and evaluation stay in the README and [`DEVELOPMENT.md`](../docs/DEVELOPMENT.md).

**Nothing it does not do.** A second research pass proposed a spreadsheet filling in, a clickable value and a review queue. The project has none of these, so the video does not show them:

- The flagged value carries the label "A person checks", and no review screen is shown.
- "Your spreadsheet" appears only in the call to action. Connecting the result to the client's own tools is part of the service.
- The hook says only that there is a faster way than typing; no amount of time saved is claimed, because none was measured.
- A total shows as the pipeline keeps it ("23.4"), with the printed form beside it (D15).

**How it is told.** These choices follow the research for #45. Where the evidence is weak, it is marked.

- **The outcome first.** Google's ABCD guidance for video ads says to "front-load your story arc". The research read that guidance in search snippets, because its pages refused automated reads. Upwork's cover preview plays only the first seconds. So shot 1 is the receipt already done.
- **The problem next, then one idea per shot.**
- **Short.** Nielsen Norman Group: "Typically, Web videos should be less than a minute long" ([NN/g](https://www.nngroup.com/articles/talking-head-video-is-boring-online/)).
- **The receipt beside its values, with each value's words highlighted.** This follows Mayer's spatial contiguity and signaling principles ([Mayer & Fiorella](https://www.cambridge.org/core/books/cambridge-handbook-of-multimedia-learning/principles-for-reducing-extraneous-processing-in-multimedia-learning/F29A19FCD34C542806F736E0661C05F5)). Those are learning studies, so here they are a guide only.
- **The look is our own judgment:** a light palette with one brand colour, paper with soft shadows, a highlighter, and one call-to-action button. The research found no study on these.

**Headlines.** There are at most 2 lines of 42 characters ([Netflix timed text style guide](https://partnerhelp.netflixstudios.com/hc/en-us/articles/217350977)). This video holds itself to 15 characters per second; that limit is our own judgment, because the viewer also reads the receipt. Line breaks fall at the end of a sentence where they can. Text contrast is at least 4.5:1, per [WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Tests check all of this, and that no developer term ("eval", "update", "ship"...) reaches the screen.

**Drawn with Pillow, encoded with ffmpeg.** Pillow was already a dependency, so no new one was added (YAGNI). Remotion would render React animations, and it is free for teams of up to 3 people ([pricing](https://www.remotion.dev/docs/license/pricing.md)), but it would add a Node toolchain for transitions that ffmpeg handles here. The container is Debian with ffmpeg, pinned by digest, and gives the same encoder everywhere.

**Where it is published, and its limits.**

- An Upwork portfolio project takes one MP4 of at most 60 s and 100 MB ([Upwork support](https://support.upwork.com/hc/en-us/articles/4402033684115-Add-Video-to-Your-Project), read in a browser on 2026-11-21).
- A GitHub attachment takes MP4 (H.264 recommended) up to 10 MB on a free plan ([GitHub Docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)).
- The README embeds the MP4 as an uploaded attachment, not committed: a regenerated binary would grow the history.
- The closing frame carries no link or contact. Upwork's rules on contact details in portfolio files could not be read, and in the README the video already sits on GitHub.

### Decisions (#60)

**An image, not a second video.** The issue first asked for a video of the delivered flow. Research found no evidence it would win clients:

- No independent study links video in a freelancer portfolio or on a B2B service page to more hires. The largest observational dataset found saw video not lift landing-page conversion, and sometimes hurt it ([Unbounce](https://unbounce.com/landing-page-optimization/video-on-landing-pages), about 35,000 pages, correlational).
- Buyer surveys rank trials, demos and reviews highest ([TrustRadius 2026](https://hginsights.com/news/trustradius-2026-b2b-buying-disconnect-report-reveals-ai-has-changed-how-buyers-research-but-not-what-they-trust/), [Forrester 2026](http://www.forrester.com/blogs/state-of-business-buying-2026/), both on software buying). Here the trial is the free sample the video already asks for.
- A folder, a schedule and a spreadsheet are static, and video cannot be scanned ([NN/g](https://www.nngroup.com/articles/video-usability)).
- Video work costs the owner several rounds of review.

**Cropped to one receipt.** The first draft showed all ten rows at 22 px, which would shrink to about 14 px at the 1000×750 size Upwork checks for sharpness. It also gave every row the same weight. Text shrinks with the image, and a crop should keep the detail that carries the meaning ([NN/g](https://www.nngroup.com/articles/big-pictures-small-screens/)). Screenshot guides say the same: show the smallest area that proves the claim, with one or two annotations ([example](https://www.pravinkumar.co/blog/how-to-design-a-product-screenshot-that-explains-itself-2026); expert opinion, no controlled study found).

- The image shows the five rows of the receipt with a value to check, at 28 px. A test holds the grid to at least 16 px at 1000×750; that floor is our judgment.
- Rows were cropped rather than columns, because `quote` and `note` carry the point.
- The file name moves to a label above the grid.
- The footer says what is left out: four columns, and the other receipt's rows.

**Word for word, marked outside the data.**

- The grid copies the file's rows and column names exactly, because `field_status` and `needs_review` are what the client filters. The caption names them too; the earlier "the third column" made the reader count. The test that keeps developer terms out of the words around the grid accepts only the grid's own vocabulary.
- The CSV has no colours, so the row a person checks is framed around its cells, with a "Check" tab in the margin. A fill inside the cells would show a colour the client never sees.
- The empty currency row stays: it shows that a value missing from the receipt is left empty, with the reason.

**Limits.**

- Upwork asks for 4:3, at least 1000 px wide, no side over 4000 px, under 10 MB, and no contact details. These rules were read only in search summaries, because Upwork's help pages refused automated reads ([Project Catalog images](https://support.upwork.com/hc/en-us/articles/1500011309082)). The image is 1600×1200 PNG.
- No grid imitates Excel's or Google Sheets' look.
- Text contrast is at least 4.5:1 (WCAG 2.2), and tests check it. The layout keeps at least 24 px between blocks, so they never read as one: the first draft's footer sat flush against the box above it and still rendered green.

## Decisions (#42): the voice-over

**Kokoro-82M, voice `af_heart`, chosen by ear.** Two local voices with licences that allow commercial use spoke the same six lines, labelled A and B, and the owner picked without knowing which was which. The other was Phonon 31m, voice Harper ([gradium-ai/xn-ptts](https://github.com/gradium-ai/xn-ptts)). It ranks above Kokoro in a blind-vote arena (Elo 1108 against 1060, [Artificial Analysis](https://artificialanalysis.ai/text-to-speech/leaderboard)), needs no espeak-ng, and runs on any Python. The owner still heard Kokoro as clearly better, and the video is made to be heard. `af_heart` is Kokoro's top-graded voice ([VOICES.md](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md)), in American English, the accent of most of the Upwork audience.

**Licences.**

- Kokoro's weights are Apache-2.0 ([model card](https://huggingface.co/hexgrad/Kokoro-82M)). The files the voice downloads are kokoro-onnx's ONNX conversion of those weights, from its [model-files-v1.0 release](https://github.com/thewh1teagle/kokoro-onnx/releases/tag/model-files-v1.0), and the `kokoro-onnx` package is MIT ([LICENSE](https://github.com/thewh1teagle/kokoro-onnx/blob/main/LICENSE)).
- Its phonemizer, espeak-ng, is GPL-3.0. It only runs when a clip is generated and never ships with the video or the package. The GPL FAQ treats a program's output as covered only when it copies the program's own text into it ([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#GPLOutput)). Our reading, not legal advice: the audio is not a work under the GPL.

**Committed, not generated per render.**

- ONNX Runtime's deterministic compute is off by default and promises nothing across machines ([API summary](https://onnxruntime.ai/docs/api/python/api_summary.html)). Kokoro's own PyTorch code draws random noise and phase ([istftnet.py](https://github.com/hexgrad/kokoro/blob/main/kokoro/istftnet.py)).
- In our spike, two runs on one machine gave identical samples, but a video that could change between machines is not reproducible in the sense of [reproducible-builds.org](https://reproducible-builds.org/docs/definition/).
- So the clips are recorded once and replayed, like the pipeline's answers. The six clips take about 1 MB.
- They are 16-bit PCM WAV, which Python's own `wave` module reads, so no new dependency comes in. A float WAV would also change on every run, because libsndfile stamps the time into its PEAK chunk.

**Spoken to the buyer, not read from the screen.** A line says the headline's idea in other words, because narration that repeats on-screen text word for word adds load without adding meaning (Mayer's redundancy principle, from learning studies: a guide only). The video still works muted.

**The narrator never speaks as the owner.** The voice is synthetic, so it never says "I", "me" or "my": that would pass an AI off as the person a client hires. The headline "Send me a sample" stays on screen, written by the owner. A test holds every line to this.

**Disclosed, though no rule found requires it.**

- The European Commission's guidance on Article 50 of the AI Act says a generic voice that resembles no real person is unlikely to be a deepfake ([FAQ](https://digital-strategy.ec.europa.eu/en/faqs/transparency-obligations-under-article-50-ai-act)).
- YouTube asks for disclosure when a voice makes a real person seem to say something ([YouTube Help](https://support.google.com/youtube/answer/14328491)).
- No Upwork rule on synthetic voices could be read.
- The closing frame still says "Voice-over generated by AI". It costs one line, and the whole video sells not making things up.

**Loudness: one linear gain, as loud as the peaks allow.**

- ffmpeg's `loudnorm` measures in a first pass, then scales the voice in a second. It falls back to compressing the voice on the fly if the gain would lift the peaks past the ceiling, or if the voice's loudness range is above the target range of 11 LU ([ffmpeg filters](https://ffmpeg.org/ffmpeg-filters.html#loudnorm)). The render refuses that fallback and names both causes. A lower target fixes the peaks, but not a wider range.
- Kokoro's peaks sit about 19 dB above its loudness. Reaching -16 LUFS, a common target for web speech (a convention, not a published platform rule), would need a peak limiter.
- So the target drops to what the -1.5 dBTP ceiling allows: about -21 LUFS for these lines. The voice stays exactly as approved, only scaled.
- If the video sounds too quiet beside others, the fix is a limiter before the gain.

**AAC-LC, 48 kHz, mono**, the format YouTube asks for on upload ([YouTube Help](https://support.google.com/youtube/answer/1722171)).
